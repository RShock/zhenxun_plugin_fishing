Gooboo 挖矿系统 vs S2 星穹矿脉 — 借鉴分析

Gooboo v1.6.2 (gityxs/gooboo) · S2 v4.2 · 2026-07-25

核心结论

Gooboo 是一款成熟的增量/放置类网页游戏，其挖矿系统以深度推进 + 镐子制作 + 冶炼转化 + 增强权衡 + 信标布局 + 深度居民转生为核心，拥有 9 种矿石、7 种稀有掉落、7 种冶炼锭、6 种气体、3 种转生货币和 80+ 升级项，系统复杂度极高。

S2 星穹矿脉以分层矿物 + 一阶/二阶无限 + 稳定态批量外推为核心，在天文数字处理和确定性设计上远超 Gooboo，但在玩法多样性、资源转化链、策略深度上有明显差距。

最值得借鉴的 5 项设计：

  1. 矿物转化链（冶炼炉：矿石→锭→增强）— 增加 2 层生产链
  2. 条件性稀有掉落（数学条件触发）— 增加探索感和彩蛋
  3. 全局效果注册表（mult 系统）— 更清晰的 buff 管理
  4. 深度门控解锁（每个升级绑定深度里程碑）— 自然节奏控制
  5. 信标式空间策略（在特定深度区间放置增益）— 增加布局决策

2Gooboo 挖矿核心机制拆解

2.1 深度推进模型

Gooboo 的挖矿是破层推进式：每一层深度有 durability（耐久 HP）和 toughness（护甲）。玩家镐子造成 damage - toughness 的有效伤害，耐久归零后破层进入下一深度。

// 深度耐久公式：指数增长 + 二次项
depthDurability(depth) = ceil(1.75^depth × (depth×0.1+1)² × 10)

// 深度护甲：深度 ≥10 后出现，削弱有效伤害
depthToughness(depth) = min(1eC, 1.82^depth × (depth×0.01-0.09) × 0.25 × ...)

// 击破所需次数
hitsNeeded = ceil(durability / (damage - toughness))

关键设计：护甲的存在使得伤害不够时完全无法推进（hitsNeeded = Infinity），形成硬性门控。深度 150+ 后还有额外指数衰减，深度 300+ 每 10 层有 100 倍 toughness 跳升。

2.2 矿石系统（9 种矿石 + 深度区间 + 模数）

每种矿石有 minDepth、maxDepth、modulo 三个参数，控制出现范围和递归模式：

modulo 是质数递增序列（3,5,7,11,13,17,23,29）。超出 maxDepth 后，矿石只在 modulo 的倍数深度出现且产量衰减 50%。这创造了矿石稀缺性轮转——玩家必须不断向更深处推进才能获得更高品质矿石。

2.3 镐子制作系统（最独特的设计）

Gooboo 最核心的玩法是镐子制作：玩家将多种矿石组合成镐子，获得新的 pickaxePower。制作系统包含 4 个维度的权衡：

质量（Quality）

quality = Σ(矿石.power) × (resin×0.3+1) × alloying
// alloying = 独特矿石种类数 × 0.5 + 0.5
// 鼓励使用多种不同矿石

纯度（Purity）

impurity = Π(矿石.impurity × 0.95^compress - compress×0.05)
cleanse = compress × 0.25 + 1
purity = impurity/cleanse > 1 
  ? 0.5^(impurity/cleanse) 
  : 1 - impurity/cleanse/2

压缩（Compression）：高级矿石可以压缩（消耗更多材料），降低杂质、增加清洁度，但成本指数增长。

制作概率：成功概率取决于质量 vs 当前镐力 + 纯度：

// 如果 quality × purity >= 当前power → 100%成功
// 如果 quality <= 当前power → 0%成功
// 否则按对数曲线计算概率
rngNeeded = (power/quality - purity) / (1 - purity)
chance = (2^((1-rngNeeded) × log2(1/purity+1)) - 1) × purity

使用 Golden Hammer 消耗品可跳过 RNG 直接成功。RNG 按 rngGroup 分组预生成，避免连续暴击/连续失败的差体验。

2.4 冶炼炉（Ore → Bar 转化）

7 种冶炼配方，将矿石组合转化为锭，需要时间 + 温度两个条件：

铝锭铝矿 + 花岗岩5 分钟100°C
青铜锭铜矿 + 锡矿 + 盐1 小时275°C
钢锭铁矿 + 煤8 小时500°C
钛锭钛矿 + 硫 + 硝石3 天800°C
闪亮锭铂矿 + 黑曜石30 天1250°C
铱锭铱矿 + 氦气1 年2000°C
暗铁锭铁矿+锇矿+深岩+氖气15 年3000°C

冶炼时间随已冶炼总量递增（timeNeeded × 1.0X^total），温度越高速度越快。温度通过升级 heatShield 提升。这构成了矿石 → 锭 → 增强/升级的三级生产链。

2.5 增强系统（Bar → 永久 buff + 惩罚权衡）

7 种锭各有独立的增强树，消耗对应锭升级，提供永久 buff：

铝锭制作质量 ×(lvl×0.5+1)，矿石品质 ×2^lvl

权衡机制：增强等级越高，黑曜石产量惩罚越重（0.75 × 1.5^(enhancementLevel-1)）。玩家可以随时开关增强效果来切换是否承受惩罚。这创造了"增强收益 vs 黑曜石损失"的策略决策。

2.6 信标系统（空间策略）

4 种信标可以放置在特定深度，为该深度范围内提供持续 buff：

Gooboo 最巧妙的设计是稀有掉落的触发条件，每种稀有材料都有独特的数学条件：

2.8 深度居民转生系统

深度居民是一个被动填充的转生条，基于时间而非操作：

// 转生进度（对数衰减逼近上限）
newDweller = overflow + limit - (overflow + limit - current) × (1-speed)^seconds

// 转生奖励
prestigeGain = dwellerBaseGain(capSteps) × bonus
// Green Crystal（模式0）或 Yellow Crystal（模式1）
// Ember（余烬）= 附加奖励，基于深度居民步数

转生重置：镐力、深度、矿石库存、冶炼进度、增强等级、信标——但保留转生货币和部分永久升级。6 种气体（氦/氖/氩/氪/氙/氡）作为另一种转生货币，每种影响不同的子系统（废料容量、镐力、废料产量、稀有掉落等）。

2.9 全局 mult 注册表架构

Gooboo 的核心架构是命名乘数注册表：所有 buff/debuff 都注册为命名的 mult，结算时通过 mult/get 统一查询：

// 注册 mult（在模块定义中）
mult: {
  miningDamage: {},
  miningToughness: {isPositive: false},
  miningOreGain: {},
  miningOreCap: {},
  currencyMiningScrapGain: {},
  // ...
}

// 应用效果（来源：升级、增强、信标、卡片等）
dispatch('system/applyEffect', {
  type: 'mult',
  name: 'miningDamage',
  multKey: 'upgrade_damageUp',  // 唯一来源标识
  value: Math.pow(1.12, lvl) * Math.pow(lvl*0.2+1, 2)
})

// 查询最终值（自动叠加所有来源）
finalDamage = rootGetters['mult/get']('miningDamage', basePickaxePower)

这个架构的优势：效果来源完全解耦。一个 miningDamage 可以同时被升级、增强、信标、卡片、消耗品影响，互不干扰。添加新来源只需注册一个新 multKey。

4可借鉴设计（按优先级排序）

4.1 矿物转化链：矿石 → 精炼锭 → 增强 强烈推荐

现状问题：S2 的矿物库存只能直接升级矿物等级，资源链只有一层（库存→等级），缺乏中间决策点。

Gooboo 做法：矿石 → 冶炼炉（时间+温度）→ 锭 → 增强站（消耗锭升级永久buff）→ 影响多个子系统。三层生产链创造了"先冶炼还是先升级"的资源分配决策。

S2 适配方案

在矿物等级之上增加一层精炼系统：

# 新增：精炼炉
# 矿物库存 → 精炼锭（消耗时间，按波次推进）
# 精炼锭 → 增强等级（永久buff，但一阶无限时清除）

REFINERY = {
    "stone_bar": {
        input: {"stone": 100},
        output: "stone_bar",
        timeNeeded: 1,  # 单位：日
    },
    "copper_bar": {
        input: {"stone_bar": 5, "copper": 50},
        output: "copper_bar",
        timeNeeded: 2,
    },
    # ... 每种矿物有对应精炼锭
}

# 增强效果示例
ENHANCEMENT = {
    "stone_bar": {
        effect: lambda lvl: {"depth_scale": 1 + lvl * 0.1}  # 深度推进加速
    },
    "copper_bar": {
        effect: lambda lvl: {"ore_gain": 1.1 ** lvl}  # 矿石产量
    },
}

关键约束：增强等级在一阶无限时清除（与矿物等级、库存一起），但不消耗星核。这样增强成为了每轮可选的额外投入——投入精炼时间换取当轮更快的推进，但不影响永久进度。

4.2 条件性稀有掉落：深度数学彩蛋 强烈推荐

现状问题：S2 地层发现完全确定性，深度推进没有"惊喜感"，玩家缺少探索动力。

Gooboo 做法：稀有材料基于深度的数学属性掉落（digitSum≥14、isPrime、10的幂、25的倍数），创造了"挖到特殊深度时有意外收获"的体验。

S2 适配方案

在 5 种矿物之外增加稀有矿物碎片，按深度属性触发：

# 稀有碎片触发条件（不向玩家显示条件，仅文档说明）
RARE_FRAGMENTS = {
    "星尘碎片": {
        # 深度数字之和为 7 的倍数时概率掉落
        condition: lambda depth: digit_sum(int(depth)) % 7 == 0,
        effect: "可在星核商店兑换额外星核碎片",
    },
    "共振结晶": {
        # 深度为质数时掉落
        condition: lambda depth: is_prime(int(depth)),
        effect: "当轮深度推进速度 +10%",
    },
    "深渊印记": {
        # 深度为 2 的幂时掉落
        condition: lambda depth: is_power_of_2(int(depth)),
        effect: "一阶无限时额外获得 1 星核碎片（10个=1星核）",
    },
}

设计要点：条件不向玩家显示（与恒纪元天气规则一致），仅文档说明。碎片的收益应保持温和，避免破坏星核仅来自一阶无限的约束（碎片兑换的是"星核碎片"而非完整星核）。

4.3 全局效果注册表：mult 系统 推荐

现状问题：S2 的效率目前由 tech_efficiency ^ len(techs) 单一公式决定，如果未来增加增强、信标等 buff 来源，需要统一管理。

Gooboo 做法：所有 buff/debuff 注册为命名 mult，结算时通过 mult/get(name, base) 自动叠加所有来源。

S2 适配方案

# 全局效果注册表
class MultRegistry:
    """所有 buff/debuff 来源通过 multKey 注册，查询时自动叠加。"""
    def __init__(self):
        self._effects = {}  # {mult_name: {source_key: value}}

    def apply(self, mult_name: str, source_key: str, value: float):
        """注册一个效果来源（如 upgrade_damageUp、enhancement_copper）"""
        self._effects.setdefault(mult_name, {})[source_key] = value

    def reset_source(self, mult_name: str, source_key: str):
        """移除某个来源（如增强关闭）"""
        self._effects.get(mult_name, {}).pop(source_key, None)

    def get(self, mult_name: str, base: float = 1.0) -> float:
        """查询最终值：base × Π(所有来源的 value)"""
        result = base
        for value in self._effects.get(mult_name, {}).values():
            result *= value
        return result

# 使用示例
registry = MultRegistry()
registry.apply("mining_speed", "tech_upgrade", 1.18 ** len(techs))
registry.apply("mining_speed", "enhancement_stone", 1 + stone_enh_lvl * 0.1)
registry.apply("mining_speed", "beacon_rich", 2.0)

final_speed = registry.get("mining_speed", 1.0)
# = 1.0 × (1.18^n) × (1+lvl×0.1) × 2.0

适配要点：这与 S1 钓鱼系统的 buff 管理可共用同一套基础设施。multKey 使用 来源类型_标识 格式（如 tech_start、enhance_copper、beacon_rich），确保来源可追溯、可单独移除。

4.4 深度门控解锁：升级绑定深度里程碑 推荐

现状问题：S2 的永久科技只绑定一阶次数（3/6/9/12），矿物解锁绑定深度比例。缺少更细粒度的进度门控，玩家无法感受到"挖到某个深度解锁了新东西"的里程碑感。

Gooboo 做法：80+ 个升级项每一个都绑定一个具体的 requirementValue（如深度 5、15、30、60、100、150...），到达深度后自动解锁购买权限。

S2 适配方案

在现有 4 项永久科技之外，增加深度里程碑奖励：

# 深度里程碑（在一阶循环内生效，一阶无限时清除）
DEPTH_MILESTONES = {
    1e6: {"name": "浅层勘探", "reward": "解锁猫砂石精炼"},
    1e7: {"name": "中层突破", "reward": "解锁铜须矿精炼"},
    5e7: {"name": "深层发现", "reward": "解锁紫晶猫眼精炼"},
    8e7: {"name": "地心逼近", "reward": "精炼速度 +20%"},
}

这些里程碑在每轮一阶循环中重新达成，为重复重玩提供节奏感和短期目标。

4.5 信标式空间策略：勘探信标 可选

现状问题：S2 的深度推进是线性的，没有"在哪个深度区间投入资源"的决策。

Gooboo 做法：信标可以放置在特定深度，为该区间提供 buff，但移除有 20 小时冷却，且同时只生效一个。

S2 适配方案

# 勘探信标：玩家在一阶循环中放置，为特定深度比例区间提供增益
BEACONS = {
    "rich": {
        name: "富矿信标",
        range: 0.1,  # 覆盖深度比例 10% 的区间
        effect: "该区间内矿石产量 ×2",
        cost: "消耗当轮部分矿物库存",
    },
    "piercing": {
        name: "穿透信标",
        range: 0.05,
        effect: "该区间内深度推进速度 ×1.5",
    },
    "wonder": {
        name: "奇迹信标",
        range: 0.05,
        effect: "该区间内稀有碎片掉率 ×3",
    },
}
# 约束：每轮最多放置 2 个信标，一阶无限时清除

信标系统需要在网页 Demo 中配合可视化（在深度进度条上标记信标位置），在 bot 场景中可通过命令放置。鉴于 S2 的低频交互特性，信标可以作为每轮开始时的战略部署——玩家选择在哪个深度区间放置信标，然后挂机等待推进到该区间时生效。

4.6 概率性制作：矿物合成 可选

Gooboo 做法：镐子制作有成功概率，取决于质量/纯度/当前镐力。Golden Hammer 可保底。

S2 适配考量：S2 目前采用确定性扰动（±2%），引入概率制作需要谨慎。如果要做，建议作为可选的高风险高回报机制，而非核心路径：

# 矿物合成：将多种矿物合成为高级矿物，有失败概率
# 成功：获得目标矿物 + 等级提升
# 失败：消耗矿物但不获得产物
# 使用"星核保底券"可保证成功

synth_chance = min(1.0, base_quality / target_quality × purity)
# 与 Gooboo 类似的概率曲线，但保底券用星核碎片兑换

谨慎引入概率可能与 S2 的确定性设计哲学冲突。如果团队偏好确定性，可改为必成功但有成本递增的合成（类似当前的矿物升级，但跨矿物合成）。

5不建议借鉴的部分

5.1 80+ 升级项的规模 不借鉴

Gooboo 的 80+ 升级项虽然提供了丰富的进度感，但维护成本极高，且大部分升级是简单的数值乘数堆叠。S2 的 4 项永久科技 + 深度里程碑已经能提供足够的进度感，且更符合低频交互的 bot 场景。

5.2 实时 tick 结算 不借鉴

Gooboo 每秒 tick 的实时结算适合网页游戏，但 S2 运行在 bot 环境中，波次结算（每日 4 波）更适合。实时 tick 会增加数据库读写频率和 CPU 开销。

5.3 RNG 分组系统 不借鉴

Gooboo 的 RNG 分组（rngGroup）用于改善制作概率的体验公平性。S2 采用确定性扰动，不需要 RNG 公平性机制。如果引入概率制作，可使用更简单的伪随机（PRD）即可。

5.4 6 种气体的复杂转生货币 不借鉴

Gooboo 的 6 种气体各自影响不同子系统，增加了策略维度但也大幅增加了理解成本。S2 的单一星核货币更清晰，且星核"仅来自一阶无限"的约束是核心设计，不宜稀释。

5.5 与主游戏深度联动 不借鉴

Gooboo 的挖矿与村庄、卡片、宝石等系统深度联动。S2 明确设计为"完全独立"（不消耗鱼竿、不读写钓鱼金币），这一约束应保持。

6S2 已有的优势（应保持）

6.1 稳定态批量外推 S2 独有优势

S2 的二阶无限目标 10^308 通过稳定态单循环采样 + 批量外推实现 O(1) 复杂度，这是 Gooboo 完全没有的架构。Gooboo 依赖 JS 原生浮点数和 buildNum 格式化，遇到大数时只能靠格式化"遮掩"精度丢失。S2 的设计从根本上解决了天文数字的结算问题。

6.2 确定性扰动 S2 独有优势

S2 的 1 + 0.02 × [-1, 0.5, 1, -0.5] 扰动模式每 4 波零均值、完全可复现，使测试可以精确验证。Gooboo 的随机掉落和制作概率难以测试和平衡。确定性设计是 S2 的核心优势，新功能应尽量保持可复现性。

6.3 低频手动批量操作 S2 独有优势

S2 的"一次访问批量购买最多 3 级"设计完美适配 bot 场景，玩家不需要高频交互。Gooboo 的实时点击式玩法不适合 bot。新增的冶炼/增强等功能也应遵循"批量操作"模式（如一次冶炼多批、一次增强多级）。

6.4 前三轮完整手动重玩 S2 独有优势

S2 要求前 3 次一阶无限必须完整手动操作，确保玩家理解所有机制后再解锁自动化。这种"先体验后自动化"的设计比 Gooboo 的"一切从开始就可自动化"更有教学价值。

7实施建议与优先级

优先级 功能 实施要点 影响范围 与现有设计兼容性
P0 全局 mult 注册表 实现 MultRegistry 类，将现有 tech_efficiency 迁移为 mult 来源之一 core 模块 完全兼容，纯重构
P1 条件性稀有掉落 新增 RARE_FRAGMENTS 配置，在 pulse() 结算中检查条件 sim_v12_layered.py, game_v4.js 兼容，不影响星核守恒
P1 深度里程碑 新增 DEPTH_MILESTONES 配置，在 discover() 中检查 sim_v12_layered.py, game_v4.js 兼容，每轮重置
P2 矿物精炼系统 新增 REFINERY + ENHANCEMENT 配置，精炼锭在一阶无限时清除 新增模块, GAME_DESIGN_V4.md 需验证平衡性
P3 勘探信标 新增 BEACONS 配置，需配合 UI 可视化 新增模块, 网页 Demo 需 UI 支持
P4 概率性矿物合成 可选功能，需团队讨论是否引入概率 新增模块 与确定性哲学冲突

最终建议

建议优先实施 P0（mult 注册表）作为基础设施重构，为后续功能铺路。然后实施 P1（稀有掉落 + 深度里程碑）——这两项改动小、不破坏现有平衡，但能显著提升探索感和节奏感。P2（精炼系统）是最大幅度的玩法扩展，需要在模拟器中验证平衡性后实施。P3/P4视团队精力和玩家反馈决定。

所有新功能必须遵循 S2 的核心约束：确定性扰动、低频批量操作、星核仅来自一阶无限、前三轮手动重玩、一阶无限清除本轮状态。
