# S2《星穹矿脉》测试准则：黑盒怎么玩、白盒怎么改

> 这份文档不是"测试覆盖率报告"，是**流程准则**。它把 2026-09/10 几轮改造里真实踩过的坑固化下来，
> 目的是让下一个接手的人（人或 AI）不必重新踩一遍。每一条后面都附了它是被哪次事故换来的。
>
> 配套：`CHANGELOG_2026-10-02_评审处置与代码改动.md`（改动明细）、`DESIGN_INTENT.md`（设计意图）。

---

## 零、一句话总纲

**黑盒负责回答"这游戏好不好玩、有没有坏"，白盒负责回答"我这次改动有没有弄坏别的地方"。两者都不能替代对方，而且黑盒的结论优先级更高——因为玩家只会看到黑盒。**

## 一、黑盒准则（浏览器实跑）

### B1. 结论必须来自实际游玩，不许从代码推断

读代码得出的"应该会怎样"一律不算数。本项目有过至少三次"读代码判断是假象、实跑发现是真 bug"的记录，最典型的一次：

> 评审里写的 P0-3「开挖后时间不走」，第一反应是"测试工具的假象"。实跑后发现**启程后时间确实卡住 30 秒**，是真 bug。

反过来也有："手动 vs 自动"的对照实验做了两版都作废，因为脚本点中的是【升级1级】而不是【完成调试】/【批量建设】——**脚本点错按钮比代码读错更隐蔽**，所以每次实跑都要把点击到的元素文本打印出来核对。

### B2. 只用玩家按得到的按钮；调试按钮的结论不可信

页面上的时间控制分两类，必须严格区分：

| 类别 | 按钮 | 能不能用来下结论 |
|---|---|---|
| 正常玩法 | 连续挖矿（`#toggleButton`）、推进 1 天 | ✅ 可以 |
| 调试 | 推进 1 秒 / 1 小时 / 20 小时 / 3 天 / 30 天、重置测试进度 | ❌ 只能用来快速到达某个状态，**不能用来测时长** |

**事故原文**：用【推进30天】一路快进，通关日算出来是 **D153**；换成每次只推 1 天，同一套数据得到 **D127**。差了 26 天。原因是大步快进会跳过一部分核心自动购买（当时的 `voyage #8` 既有失败）。

> **铁律：所有时长结论，只认"1 天步进"或无头模拟器（`s2_galaxy_replay.mjs`）。** 两者互相印证才算数。

### B3. 每次实跑都必须抓 JS 错误，0 报错才算通过

```python
errs = []
pg.on('pageerror', lambda e: errs.append(f'PAGEERROR {e}'))
pg.on('console', lambda m: errs.append(m.text) if m.type == 'error' else None)
```

数值对了但控制台在刷红，等于没通过。本项目交付前的每份实跑报告末尾都有一行 `JS 错误: 无`。

### B4. 从清档开始，固定 seed，记录"玩家可感知指标"

```js
localStorage.clear()   // 清档
```
每次实跑必须清档重开，否则残留存档会让"新手引导"类的逻辑整段测不到（前 5 次手动启程、首星教学期都只在新档出现）。

要记录的不是内部状态，而是**玩家在结算页能看到的东西**：通关天数、挖穿星球数、**操作次数**、亲手/助手/自动的级数分布、最终倍率、称号文案。这组指标能一眼看出"这局是怎么赢的"。

### B5. 画像对照：至少跑满四象限

| | 夜班助手 开 | 夜班助手 关 |
|---|---|---|
| **每天上线一次** | D120.6 | D124.6 |
| **完全不操作** | **D125.6** | 589 天只挖 31 颗（不通关） |

四个格子都要有数。**"完全不操作 + 默认配置"这一格是硬指标**——它直接回答"躺平玩家能不能通关"，而这是本项目被推翻过一次的核心设计决策。只跑 daily 画像会让你对默认体验一无所知。

### B6. 文案和数值一样重要

实跑时要顺手检查的几类文案问题（都真实出现过）：

- **科学计数法残留**：`1.23e+21` 直接糊到玩家脸上。检查方法：全页 `innerText` 正则 `/\de[+-]\d/`。
- **术语漂移**：同一个概念在三个地方叫三个名字（"完成调试"/"亲手建设"/"手动购买"）。
- **条件未渲染**：奖励写着"完成奖励：+3 核心"却没说"买什么由你决定"，玩家不知道这核心能干嘛。
- **数量级中文化**：`2728.2万` 比 `27282000` 好读，群聊场景尤其。

### B7. 交付载体决定验收口径

本项目真正的载体是 **QQ 群聊**，网页只是模拟器。所以验收时要反复问："这一步在群里怎么发？"
由此推出的硬约束（已写进 `DESIGN_INTENT.md`）：**一天最多 6 次升级操作**、自动游玩只在每天 24:00 触发并尽量买满。
任何在网页上"手感不错"但需要玩家一天点十几次的设计，在群聊里都是不可接受的。

## 二、白盒准则（`node --test` 回归套件）

### W1. 动手之前先跑基线，并把基线失败集合记下来

```bash
git archive HEAD | tar -x -C /tmp/base     # 导出改动前的树
node --test *.test.mjs                     # 跑基线，记录失败清单
```

**事故原文**：仓库自带 5 个 `*.test.mjs` 共 56 条用例，我改了大半轮数值才想起来跑，一度累积 **17 条回归**。有了基线对照才能把"我弄坏的"和"本来就红的"分开，最终收敛到**我引入的回归 = 0**。

> 没有基线，你会在"修别人的历史问题"和"修自己刚弄坏的东西"之间彻底迷失。

### W2. 夹具可以改，断言里的设计意图不能改

这是最重要的一条。改测试时先分清你在改什么：

| 类型 | 例子 | 能不能为了变绿而改 |
|---|---|---|
| **夹具/脚手架** | 合成存档时忘了算星区奖励核心、忘了换星后矿币清零 | ✅ 应该机械对齐新规则 |
| **描述性快照** | "前十天每日购买级数 `[6,2,3,...]`" | ⚠️ 可以重录，但必须在 CHANGELOG 写明旧值作废的原因 |
| **设计意图数值** | "压轴科技终局占 ×9.3"、"每级增益 2.0" | ❌ **不许改断言，要改就去改设计** |

**事故原文**：我曾把 6 项 `maxLevel=3` 的压轴科技提到 5 级、效果按比例缩小，想让它们也走完"3 级手动 + 2 级自动"。`voyage #15/#17` 立刻报 `520 !== 850`、`1.6 !== 2`。
**正确处置不是改断言，而是回退那 6 项的分级设计**——因为 `maxLevel=3` 恰好等于转自动门槛，它们天生就是"全程亲手"，这是规则的自然结果。两条用例自己就绿了。

> 一条断言红了，先问"它在保护什么"。保护设计意图的断言红了，说明**你的改动错了**。

### W3. 守恒律 > 具体数值

能写成守恒的，就不要写成常量。常量会被每次数值重排打穿，守恒律不会。

```js
// 差：assert.equal(engine.state.cores, 26)        ← 数据一动就红
// 好：余额 + 已花费 = 理论产出
assert.equal(engine.state.cores + coreSpent(engine), 21 + 3 + 12);
```

本项目在用的守恒律：**核心守恒**（余额 + 各科技等级反推的花费 = 星球产出 + 星区奖励）、**等级守恒**（亲手 + 助手 + 自动 = 总级数）、**存档往返恒等**（`new Engine(snapshot).snapshot() === snapshot`）。

### W4. 上限断言要绑定"与什么成正比"，不要写魔法数

```js
// 差：assert.ok(summary.compiled <= 80);
// 好：重编次数跟"买了多少级科技"走，而不是跟几千万颗星球走
assert.ok(summary.compiled <= data.prestige.upgrades.reduce((n, s) => n + s.maxLevel, 0));
```

性能类断言要守住的是**复杂度的阶**（与星球颗数无关），不是某个具体数字。机制一改，魔法数必红，而阶的断言会继续有效。

### W5. 快路径必须和"笨实现"对答案

引擎里凡是有"批量结算/前缀和/二分"这类加速路径，就必须有一条用例用**最笨的逐颗循环**算一遍对照：

```js
fast.mineBlock(totalMinutes);               // 批量结算
for (let i = 0; i < 151; i += 1) { ... }    // 逐颗循环，绝不碰批量 reducer
compare(fast.snapshot(), slow.snapshot(), "", 20);
```

注意两个坑：
- 参考循环要**完整模拟引擎的每一步**（`finishPlanet()` → `autoPurchaseCore()` → `departPlanet()`），漏一步就会假报警；
- 自动购买会**改变后续航程长度**，所以参考循环必须逐颗重算计划，不能复用同一份 plan。

### W6. 大步快进必须等于小步快进

这是本项目吃过最大亏的一条（见 B2 的 D153 事故）。对应的白盒用例：

```js
a.mineBlock(14400);                                   // 一步推 10 天
for (let i = 0; i < 1440; i += 1) b.mineBlock(10);    // 1440 个 10 分钟
compare(a.snapshot(), b.snapshot());
```

**根因模式要记住**：`advanceVoyages` 这类批量路径里**没有每日/每小时 tick**。任何把新机制只挂在 `mineBlock` 的 tick 上的实现，在批量路径里都会失效。新增定时行为时，先问"批量结算路径上它会被触发吗"。

### W7. 存档必须原子失败

`restore()` 的契约有三条，缺一不可：

1. 任何一处字段损坏 → **整份拒绝**（抛错），不做"半吊子兼容"；
2. 失败后引擎状态**必须和调用前完全一致**（`assert.deepEqual(e.snapshot(), saved)`）；
3. **不修改传入的快照对象**（调用方还要用它）。

用例写法是列一串"损坏姿势"逐个过（本项目 15 种：删字段、改类型、等级越界、亲手级数 > 总级数、已转自动但亲手不足、核心对不上账、历史重复、时钟倒流、旧版本号……）。

> 相关决策：**旧存档迁移在 2026-10-02 整体删除**。理由是 demo 没有真实玩家存档，而迁移分支是全仓库最大的一块"无人覆盖的死代码"。如果将来真上线了，迁移要重新写，并且**每一个迁移分支都必须有用例**。

### W8. 不要写死受数据重排影响的门槛

```js
// 差：fixture({ resets: 1200 })             ← 为了测 big_bang，写死了它当时的解锁点
// 好：fixture({ resets: data.prestige.upgrades.find(u => u.key === "big_bang").unlockResets })
```

解锁点、价格、目标星球数都会随平衡调整搬家。用例要**跟着数据走**。

### W9. 标定值必须由工具推导，不许手填

通关目标 `galaxyTargetPlanets` 的定义是"全部科技研究完成后，再留 5 天纯产能"。它只能由 `s2_galaxy_replay.mjs --calibrate` 反推：

```bash
node s2_galaxy_replay.mjs --calibrate --days 600
# → recommendedTarget: 27282000（研究 D115.59 完成 / 1800 万颗，终局 0.04654 秒/颗，尾段 5.0001 天）
```

并且有一条用例（`voyage #22`）专门盯着"数据里的值 == 标定器推出来的值"。手填必红。

### W10. 浮点：相对 + 绝对双容差，累加误差按步数放宽

```js
function close(a, b, label = "", scale = 1) {
  assert.ok(Math.abs(a - b) <= scale * (2e-7 + Math.max(Math.abs(a), Math.abs(b)) * 2e-10), `${label}: ${a} != ${b}`);
}
```

逐颗累加 151 次的参考实现，比一次性批量计算多攒约 20 倍舍入误差，这种地方要显式传 `scale`，而不是全局放宽容差（会让真 bug 溜过去）。整数字段（核心、等级、星球数）**必须精确相等**，用正则按字段名区分。

### W11. 共享引用陷阱

```js
this.rules = data.rules;   // engine.js:179 —— 这是引用，不是拷贝
```

测试里想改规则（例如把"前 5 次手动启程"置 0 以隔离教学期），**必须先克隆整个 data**，否则会污染同一进程里所有后续用例。本项目因此否决过"给 state 加一个 `handDepartures` 计数字段"的方案，改用"夹具克隆 data 把 `manualDepartures` 置 0"。

### W12. 用基线快照锁住"已认可"的时段

教学期（前 30 天）是作者逐帧认可过的，任何改动都不该波及它。做法是把五种画像 30 天后的结果钉在仓库里：

`thirty_days_baseline.json` = 矿币 / 深度 / 事件序列指纹(sha256) / 随机数状态指纹 / 首星是否挖穿 / 核心余额。

> 原先这条回归是跟历史提交 `git show 8da6657:` 对比的。**不要依赖历史提交对象**——克隆可能是浅拷贝（本项目就是，`git fetch --unshallow` 也没补回来），而且一旦时段本身被有意改过，对比就永远不可能绿。改成仓库内基线文件，并在用例注释里写明"重录前请确认是有意为之"。

## 三、什么时候可以删测试

删测试是严肃操作。只有以下三种情况允许删，且**必须在 CHANGELOG 里逐条写明删了什么、为什么**：

1. **功能已移除**：用例测的东西不存在了（例：五路线托管删除 → `voyage #18` 五路线 bootstrap；旧档迁移删除 → 5 条迁移用例）。
2. **依赖取不到的外部对象**：依赖历史提交、依赖已删除的参考实现（例：`git show 8da6657:` / `25f9313:`）。**优先找替代品**（见 W12），实在没有才删。
3. **断言的是已被推翻的设计意图**：例如"完全不操作的玩家从第 4 颗起停滞"——这条在 2026-10-02 被作者明确推翻（助手默认开），用例跟着改成"托管玩家同样越挖越快"。

❌ **不允许的删除理由**："它一直红"、"看不懂"、"跑得慢"。

本轮按此准则：删 9 个文件 / 9 条用例，改预期值 7 处，新增 2 条用例 + 1 份基线，最终 **5 个文件 56 条全绿**。

## 四、怎么跑

```bash
# 白盒：全套回归（约 3.5 分钟，银河那几条单条就要一两分钟）
cd doc/s2设计/星穹矿脉/vnext
node --test s2_engine.test.mjs s2_descriptions.test.mjs s2_late_factors.test.mjs s2_prestige.test.mjs s2_voyage.test.mjs

# 白盒：四象限画像回放 + 重新标定
node s2_galaxy_replay.mjs --profile daily  --days 600
node s2_galaxy_replay.mjs --profile absent --days 600
node s2_galaxy_replay.mjs --profile absent --core-helper off --days 600
node s2_galaxy_replay.mjs --calibrate --days 600

# 黑盒：先起静态服务，再跑浏览器实跑脚本（1 天步进，约 50 秒）
python3 -m http.server 4160 --bind 0.0.0.0 --directory web/static/s2-vnext &
python3 doc/s2设计/星穹矿脉/vnext/browser_playthrough_check.py
```

`browser_playthrough_check.py` 做的事就是 B1–B6 的最小实现：清档 → 开挖 → 每天推进 1 天 → 教学期内亲手启程 → 直到通关 → 打印结算页全文 + 科学计数法检查 + JS 错误清单。**它是"准则"的可执行版本，改游戏之后应该先让它跑绿，再去看单测。**

## 五、给下一个接手的人的三句话

1. **先跑基线，再动手。** 这是本项目唯一一条用 17 条回归换来的教训。
2. **红的断言先问"它在保护什么"**，再决定是改代码还是改测试。保护设计意图的，一律改代码。
3. **时长结论只认 1 天步进和无头模拟器。** 调试按钮快进出来的数字，一个都别信。
